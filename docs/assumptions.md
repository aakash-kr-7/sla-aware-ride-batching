# Policies and modelling assumptions

The case study supplies behavior and examples, not a complete operating policy. The following are implementation decisions unless explicitly marked as source examples. Configuration defaults come from [application.yml](../src/main/resources/application.yml); tests may use different values.

| Topic | Necessary interpretation / current value | Consequence |
| --- | --- | --- |
| D01: requested time and slot | Server creation time; 15-minute UTC epoch buckets, start inclusive/end exclusive. The source's 15 minutes is illustrative. | No scheduled-time input. Creation sets the dedup slot; batch formation recomputes source windows from creation time, waits for close unless urgent, and never merges source windows. Keep duration stable with outstanding requests. |
| D02: pickup promise | Creation time + `app.sla.pickup-sla-minutes`, default 20; source gives 20 as an example. | Unassigned planning is optimistic at first pickup. Offering/new acceptance include current-time driver approach and repeat route constraints; actual arrival remains unmeasured. |
| D03/D04: dedup identity and coordinates | Four decimal places, HALF_UP, fixed in `DeduplicationKeyGenerator`; employee + both endpoints + slot form identity. | Similar points can deduplicate; routing/serviceability retain original doubles. Normalization does not guarantee all GPS jitter falls in one bucket. |
| D05: serviceable region | Active circular geofences; Haversine distance <= radius. Overlaps choose closest center then lowest numeric zone ID. | Pickup only; polygon boundaries and dropoff restrictions are absent. Cache staleness is described in the cache decision. |
| D06: direction | Leader bearing difference <= 45 degrees (`app.batching.max-bearing-angle-diff-degrees`). | Runtime groups each source window by active pickup zone and leader bearing. Unknown zones remain pending. Bearing compatibility alone does not prove a small detour. |
| D07: rider detour | Extra in-vehicle duration must meet both 100% relative and 30-minute absolute limits. | Policy chosen here, not specified by the source. Some tests/JMH use 40%/15 minutes. No claim that either policy is operationally acceptable. |
| D08: travel duration | `floor(Haversine metres * 1.35 / (30 km/h in m/s)) + 120 seconds` per leg. | Assessment approximation: constant speed/circuity/dwell, no traffic or road network. Same-location route legs still include dwell; driver approach excludes destination dwell and is zero when colocated. |
| D09: seats | One rider/booking; `app.fleet.default-vehicle-capacity=4`. Source illustrates a four-seater. | A temporary Vehicle value enforces planning capacity; no persisted vehicle allocation. Dispatch checks actual driver capacity against peak route occupancy, including at acceptance. |
| D10: cool-off | `dispatch.cool-off.duration=PT5M`; excludes a driver for the same trip if a REJECTED offer was updated strictly after now minus duration. | Measured from rejection; equality ends temporary policy exclusion. The connected dispatch workflow has a stronger no-repeat rule for all drivers already attempted on that trip, even after cool-off ends. No trip revision reset. |
| D11: cancellation | State-idempotent; only before any pickup in the trip; remove/resequence affected stops, recalculate arrivals, cancel empty trip. | Empty-trip cancellation expires outstanding offers and releases its assigned driver atomically. Remaining order is preserved. Recompute from max(current time, original planning start), plus current driver approach for an accepted trip. Recheck capacity/detour and remaining pickup deadlines and persist one OPEN risk per booking/reason. Execution-time cancellation is unsupported. |
| Trigger policy | Batch scheduling off by default; enabled fixed delay is 5000ms. Every newly planned trip attempts dispatch. | Collection slots and batch frequency are separate. Expiry scheduling is independently enabled by default every 5000ms. Batch cycles separately claim up to the configured claim limit of expired requests without an OPEN missed-promise issue. |
| Collection urgency and bounds | `app.batching.max-bookings-per-cycle=100` (1–1000); `app.batching.urgent-lead-time-seconds=300` (positive). | Claims order by deadline/creation/ID. Open windows may process early at the urgent cutoff. Expired/future requests are excluded. Limits/workers may fragment clusters; the guard is not an overload guarantee. |

Dispatch additionally uses `dispatch.offer-lifetime=PT2M`, `dispatch.max-offers-per-trip=3` (1–100), and `dispatch.expiry-scheduling.max-trips-per-cycle=100` (1–1000). Attempt history is durable; no successful response resets it. Empty eligibility is visible and requires explicit Advance after availability changes; the expiry job only scans existing due offers. Admin simulation responses use the driver on the stored offer, without accepting caller-supplied driver IDs.

The limits above describe computed acceptance, not real-world pickup or road-ETA guarantees. Seat capacity bounds simultaneous riders, not total route stops; batch formation's explicit claim limit bounds planner input. It does not bound database scans, active-zone count or the separate late-insertion path. Exact eligibility, deadline equality and pending-count semantics are in [batching strategy](batching-strategy.md); cheapest-feasible search and assignment timing are in [planner and ETA policy](planner-and-eta.md).

## Environment and possible production work

Normal startup requires a database password and JWT signing secret. Compose reads `.env`; Spring Boot needs exported values. The `local` profile can create only an explicitly enabled admin in an empty account table. The separate `local-fixtures` profile supplies disposable accounts, zones and drivers in its own database, uses a 20-minute urgent guard and ten-minute offers, and leaves route constraints unchanged. Tests use separate signing material and disposable PostgreSQL. See [local development](local-development.md) for the exact differences and [traceability](requirements-traceability.md) for requirement coverage.

CONFIRMED is route association, not driver acceptance. Admin-only ordered pickup/dropoff simulation makes execution states reachable; first pickup starts the trip and final dropoff releases the driver. Expired solo promises stay pending with one persisted OPEN issue; cancellation resolves automatic booking issues. See [lifecycle policy](booking-lifecycle.md).

Road-network/traffic ETA, actual driver execution evidence and operational remedies for missed promises are future improvements. They are not properties of the current submission.
